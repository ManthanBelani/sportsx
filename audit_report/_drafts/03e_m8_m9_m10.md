## M8 — Leaderboard

### M8.1 Athlete leaderboard (podium + 4–10, filters, verified points) — **PARTIAL** — Severity: **HIGH**
Two separate boards exist and they disagree on the core rule:

**Season board `GET /leaderboard`** (`app/Http/Controllers/LeaderboardController.php`)
- L21–46: filters `sport_id|city_id|age_group_id`, limit ≤ 50, podium = top 3 + `ranks` 4–10 (L52–53). OK.
- Points from `LeaderboardScore` rows built by `app/Services/LeaderboardService.php::recalculateForAthlete` (L68–120):
  - L81–90: achievements filtered `is_verified=true` **or** `verification_status='verified'` — **but the `achievements` table has neither column** (migrations `2026_08_18_000001_create_achievements_table.php` = only id/athlete_id/text/sort_order/timestamps; `2026_10_14_000001_phase2_privacy_pivots_achievements.php` adds title/type/sport_id/level/year/certificate_media_id/coach_profile_id — no verification column). `Schema::hasColumn()` both false → **every self-declared achievement counts**. There is no admin endpoint to verify an achievement either (routes/api.php L440–444 = owner-only CRUD; grep of Admin controllers shows no achievement verification).
  - Achievement points are **uncapped**: `count() * pointsPerAchievement()` (L90) with no max. A user can `POST /me/achievements` N times ("comment" is free-text, no verification, no dedup, no rate limit beyond sanctum) and add 50·N points. Participation is capped (L113, cap default 50, admin-tunable), achievements are not.
  - L92–99: completion milestone ≥80% = 20 pts (CompletionChecklistController).
- Minor anonymization **correct** here: LeaderboardController::present L74–86 → first name + initial; `guardianOptedIn` L100–110 requires `GuardianConsent.consent_status='verified' AND leaderboard_name_mode='full'`.

**Athlete board `GET /me/leaderboard`** (`app/Http/Controllers/AthleteLeaderboardController.php`)
- L45–58: periods weekly/monthly/season/allTime, categories xp/matches/wins/achievements/connections. Computed live.
- L171–184 `achievementCounts()`: **no verified filter at all** — counts every achievement row. Direct violation of rule 8 ("points from verified achievements"); XP board L157–169 = 50/achievement uncapped + capped match bonus.
- L224–285 `winCounts()`: 1st places matched to athletes **by string name** (`winner_name` vs `full_name`/`user.name`/`team_name`, L238–281) — name collisions credit multiple athletes (L255 merges); spoofable by registering a team named after another athlete.
- L66–68: loads **every** `AthleteProfile` row into memory each request, then scores in PHP — O(all athletes) per request, no caching. Will not scale.
- Minor anonymization correct (L328–342, L375–385 — same GuardianConsent gate).

**Recompute integrity**
- `RecalculateLeaderboardJob` scheduled daily 04:00 (`routes/console.php:35`) and dispatched only on achievement **create** (`AchievementController.php:68–73`). Achievement update/delete and registration approval/rejection do NOT trigger recalc (`RegistrationActivityService.php` has no leaderboard calls) → season board participation points go stale up to 24h.
- Admin rebuild endpoint `POST /admin/leaderboard-config/reset` (`AdminLeaderboardConfigController.php:53–60`) exists and is inside the admin route group (routes/api.php L600+).

**Abuse summary (rule 8 broken):** unverified/self-declared achievements count on both boards; achievement points uncapped; no verification workflow exists; wins matched by name. The "counts ONLY verified achievements" requirement is enforced nowhere because the schema makes it unenforceable.

Gaps: add `achievements.is_verified` + admin verification queue; cap achievement points; filter /me/leaderboard by verification; trigger recalc on registration approval; name-collision guard for wins.

### M9.2 Push notifications (FCM) — **PARTIAL** (pipeline solid; per-event gaps + known bug confirmed) — Severity: **HIGH**

Pipeline (healthy):
- Token registration: `POST/DELETE /me/device-tokens` (`NotificationController.php:84–129`, upsert + soft-deactivate). Flutter registers on init and on auth (`push_notification_service.dart:123–192`, `auth_provider.dart:310,432`), `onTokenRefresh` re-registers (L162–169). `PruneStaleDeviceTokensJob` scheduled daily 03:30 (`routes/console.php:31`).
- `NotificationService::create` (`app/Services/NotificationService.php:66–134`): in-app row first → category gate → `SendPushNotification` chunked (batch 500) on `push` queue → push_status tracked (queued/suppressed/no_devices/sent/partial/failed) → **email fallback** when no tokens or all sends fail (`emailFallback` L137–151; job `SendPushNotification.php:77–84`). Double-fan-out prevented (`SendPushNotificationListener` is an intentional no-op).
- Token lifecycle: `UNREGISTERED` retires immediately, transients 3-strike via `recordFailure()` (`SendPushNotification.php:51–64`).
- `FCMService` = HTTP v1 with service-account auth, Android channels per type (`FCMService.php:38–66`), channels created client-side with matching ids (`push_notification_service.dart:27–55`).
- Deep links: `action_url` persisted, serialized in `toPushPayload` (`Notification.php:147–162`), parsed and navigated client-side for cold-start (`getInitialMessage`), background tap (`onMessageOpenedApp`), and foreground local-notification payload (`push_notification_service.dart:42–48, 75–84, 138–159`). The push service's `navigatorKey` is the same key the GoRouter uses (`core/router.dart:250` imports it from `push_notification_service.dart`). Foreground handling **exists** (contrary to the prior "absent" note): `onMessage` shows a local banner + refreshes the bell (L149–152). Background/terminated data-only messages are queued into SharedPreferences by `firebaseMessagingBackgroundHandler` (L262–284) and replayed after auth (`processPendingNotifications`, `auth_provider.dart:312`).
- Prefs: `NotificationPreferenceController` validates global push + 6 categories; `prefsFor()` merged defaults; non-override push suppressed per category while in-app row survives (`NotificationService.php:96–104`).

**HARD_OVERRIDE_TYPES confirmed** (`NotificationService.php:22`): `['account_action', 'registration_approved', 'registration_rejected']`.

**Known bug CONFIRMED — registration outcomes are typed `status_update`:** every notification in `RegistrationController.php` uses `'type' => 'status_update'` — approved (L201–206, L266–271, L426–431), rejected (L174–179, L231–236), and new-registration-request to organizer (L72–77, L347–352). The strings `registration_approved`/`registration_rejected` appear **nowhere as created types** (only in the Events-tab filter, `NotificationController.php:33`). Consequences: (a) outcome pushes are silently suppressed if the user disabled the `events` category or global push — spec lists "registration updates" as a must-reach P0; (b) categoryFor('status_update') → `people` (no keyword match → default), so outcomes are even filed under **People**, not Events — the Events tab filter compensates via explicit type list but `status_update` is ALSO in the People tab list (L26), so outcomes appear in both tabs while matching neither keyword category.

**Per-event FCM audit (default prefs = all on, so these DO send by default):**
- Follow: `FollowController.php:53–58` — sends (type `status_update`).
- Connection request/accept: `ConnectionController.php:74–114` — sends.
- Messages: `ConversationController.php:188–193` — sends (type `message` → `mentions`).
- Enquiries: **new enquiry sends NOTHING** — `EnquiryController::store` (L12–48) creates Enquiry + first EnquiryMessage and returns 201 with no NotificationService call; only *replies* notify (`enquiry_reply`, L123–131). Owner learns of a new enquiry only by polling the inbox. Spec lists "enquiries" as P0 push → **gap (HIGH within feature)**.
- Verification result: `VerificationController.php:155,180` — type `account_action` = hard override → always push+email. Correct.
- Scout shortlist/connect (extra, beyond spec): `ScoutShortlistController.php:73–81`, `ScoutConnectionController.php:66–74,114–122` — send; type `status_update`.

Gaps: use the two registration_* types in RegistrationController; notify listing owner on enquiry creation; consider hard-overriding message notifications or at least filing them correctly.

### M9.3 Deadline / nearby reminders — **BROKEN (dead code path)** — Severity: MEDIUM (P1 feature)
- `ReminderService` (`app/Services/ReminderService.php`) is complete and correct in isolation: `arm()` creates `ReminderSubscription` rows at T-2d/T-1d 09:00 (L14–36), `disarm()` (L41–48), `sendDue()` fans out through NotificationService as type `reminder` (L53–75, category `reminders`, hard-notification channel exists `sportx_reminders`).

### M10.5 Contact athlete / parent (minors route to guardian) — **PARTIAL / effectively BROKEN for minors** — Severity: **HIGH**
- `POST /athletes/{id}/contact` (`AthleteContactController.php:19–69`): creates a pending `Connection` (L26–29); minor detection via DOB (L31–37).
- **The "guardian review" branch notifies the WRONG account:** minor branch (L39–49) sends the notification with `'user_id' => $athlete->user_id` — the minor's own account — titled "Scout contact request (guardian review)". The comment claims "U-18 → guardian notified" but there is **no guardian user account to notify**: `GuardianConsent` stores only `guardian_name/phone/email` strings (`GuardianConsent.php:34–36`); grep for `guardian_user_id`/guardian mirroring returns nothing. So the guardian (who may not even use the app) is never actually notified; only the minor sees it. Guardian verification is via OTP to guardian email (`GuardianConsentService.php:54–66`), no notification channel.
- Scout connect path `ScoutConnectionController::store` (L34–77) has **no minor handling whatsoever** — scout request lands directly in the minor's inbox, no guardian step, violating rule 2 ("scouts and strangers contact a minor through a request that notifies the guardian").
- Mitigation that DOES exist: chat is gated after acceptance (minor chat gate `ConversationController:239–264`, per prior trace) and `ensurePrivateConversation` (ScoutConnectionController L345–371) only fires after mutual acceptance.
- Flutter wired: `observation_provider.dart:47` posts `/athletes/$id/contact`; connect via `/scout-connect/:athleteId` (router.dart:481).
- Verdict: mechanism (connection request + label) exists; the guardian routing requirement is not met. To fix: notify guardian via email/SMS transport or a guardian-linked account, and gate ScoutConnectionController::store on minors.

## Cross-cutting checks

- **Rule 8 server-side verdict:** FAILED. Verified-only scoring is dead code (no `is_verified`/`verification_status` column on `achievements`); `/me/leaderboard` counts raw achievements; achievements uncapped and self-serve → leaderboard inflation is trivial (`POST /me/achievements` in a loop, each +50). Participation is capped and gated behind organizer approval (only genuine vector blocked). Wins matched by free-text name.
- **Rule 10 server-side verdict:** HELD for shortlists/observations (owner-scoped everywhere, no IDOR found). Eroded at the edges: shortlist-add notification reveals membership to the athlete; scout dashboard leaks minor full names.
- **Minor-name masking implementations:** correct in both leaderboard controllers (GuardianConsent `leaderboard_name_mode='full'` opt-in, verified-consent only); missing in ScoutDashboardController; discovery masks DOB/phone but not nested user contact fields.
- **Scheduler:** reminders every 15 min, leaderboard recalc daily 04:00, token prune 03:30, notification prune 03:45 (`routes/console.php:22,31,32,35`).
